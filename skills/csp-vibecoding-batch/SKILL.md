# 维护既有 Vibecoding 任务包

1. 找到现有包、适用 AGENTS、编写契约（如 `_AUTHORING.md`）、事实表、索引/矩阵、最近同类批次与包指定的实际校验入口。模板、编号、状态、所有权及命令沿用该包。没有专用校验器时用项目已有文档检查并人工核对，把缺口写明。
2. 先判增量归属：独立目标才按包规则追加批次；已归入现有卡的补充改原卡。检查批次号、依赖是否存在及无环、输入输出和写入范围；并行包从唯一协调入口更新共享文档。没有依据不编工期、环境、执行者或已完成的状态。
3. 核对当前 checkout 的每条关键源码引用：打开实际区间，检查路径、行号范围和语义。把静态确定、拟新增、待实测、待授权的结论分开。验收条件说明怎样才算通过、失败或未验证；保留原有不做范围和接续入口。
4. 在包的索引、依赖或派工表、事实记录、验收台账及适用的任务队列同步本次变化，复用原状态真源。避免复制整套业务约定，避免为立卡把既有未验项标绿。
5. 所有参与校验的文档改完后，运行包的实际校验和适用的自测，分别查看退出码、检查范围、跳过和未覆盖。若包要求存档，先输出到暂存位置，成功后替换旧证据。若回填台账又改变了校验输入，再跑受影响门禁；易变计数集中到一份证据，保持链接可查，避免互相改数字。
6. 交付卡片、影响的索引、实际检查结果和剩余边界。立卡请求以任务文档交付为止；同一请求已明确授权实现或提交时按项目流程继续。需要提交时只暂存本轮拥有的路径。

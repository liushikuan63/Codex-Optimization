# SPA 白屏与卡在加载态

用实际失败 URL 复现，先保存首次加载的截图、浏览器控制台和请求时间线，记录页面、构建标识、前端与请求目标。涉及缓存或 Service Worker 时，先保存当前会话的证据；再用隔离配置作对照，避免清掉用户原现场。

| 查哪一段 | 要辨别的证据 |
| --- | --- |
| 文档与版本 | 文档响应、构建标识、HTML 引用、缓存来源与 Service Worker 控制状态；当前会话与干净会话是否拿到不同版本 |
| 入口与分包 | 模块入口、懒加载 chunk 的 URL、状态、类型及正文；SPA 回退可能返回 HTTP 200 的 HTML，仍算脚本加载失败 |
| 启动依赖 | 按请求时序核对必需 API 的 pending、超时、状态、响应类型与应用契约；区分鉴权、后端错误、代理回退，以及其中哪个会阻止启动 |
| 应用状态 | 资源和请求完成后，确认是否挂载、是否退出 loading，以及异常、取消和切路由是否留下旧请求、旧状态或被吞掉的错误 |

修复前后沿同一路径核对预期业务控件；涉及路由时测直接打开、刷新及站内导航。导致旧执行上下文销毁的导航后重新获取页面/元素，按新 URL 和可观察的就绪条件继续读。状态码、页面标题和根节点存在各自都不足以证明业务就绪。

在隔离测试环境一次只模拟一个已定位的故障，例如入口分包缺失、必需 API 返回错误或延迟。断言正常路径完成，异常在项目定义的时限内给出可见反馈并退出无期限加载态；若设计有重试，继续验证恢复。不能只等遮罩消失，也不能把“受控故障可区分”当真实线上复现。根据证据决定缓存策略和超时预算。
